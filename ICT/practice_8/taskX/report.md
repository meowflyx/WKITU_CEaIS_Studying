## 1.1. Цель и выбор задания

Цель работы: описать восемь операций библиотечного API и определить, как система должна обрабатывать повторные запросы. API является договором между программами: он задаёт доступные действия, формат сообщений и возможные результаты.

После рассмотрения всех восьми заданий выбран вариант 1. Он выполняется проектированием в текстовом редакторе, не требует программирования, внешней службы или сбора данных. По сравнению с вариантом 2 здесь не нужны измерения размера файлов, а по сравнению с вариантом 3 не требуется проверять действующий сторонний сервис. При этом все требования выбранного задания можно раскрыть полностью.

Ниже приведён проект, а не описание работающего сайта. Адреса относительные; идентификаторы и сообщения учебные. Выдачи, брони и задолженности относятся только к своей библиотечной системе. Предполагается, что библиотекарь уже прошёл проверку личности и имеет право выполнять операции.

## 1.2. Ресурсы предметной области

| Ресурс и путь коллекции | Содержание и отличие |
|---|---|
| Издания, `/editions` | Библиографические сведения о конкретном издании: название, автор, год, ISBN при наличии. Переиздание может быть отдельной записью. |
| Экземпляры, `/copies` | Физические книги с собственным инвентарным номером, ссылкой на издание и состоянием. Две одинаковые книги относятся к одному изданию, но имеют разные номера экземпляров. |
| Читатели, `/readers` | Учётные записи читателей с библиотечным идентификатором и действующим статусом. |
| Выдачи, `/loans` | Связь экземпляра и читателя, дата выдачи, срок возврата и состояние. История выдачи сохраняется после возврата. |
| Брони, `/reservations` | Место читателя в очереди на издание. Конкретный экземпляр назначается при подготовке выдачи. |
| Задолженности, `/debts` | Отдельные начисления с суммой, причиной, читателем и ссылкой на выдачу. Возврат книги сам по себе не удаляет начисление. |

Издание описывает содержание и выпуск книги, экземпляр обозначает конкретную физическую вещь. Если смешать их, выдача одной книги ошибочно сделает недоступными все одинаковые книги или позволит выдать один физический экземпляр двум людям.

Дополнительные подчинённые ресурсы отражают события: `/loans/{loan_id}/return` хранит единственный возврат, а `/loans/{loan_id}/renewals` хранит историю продлений. Они не заменяют шесть основных ресурсов.

## 1.3. Восемь операций

| № и действие | Метод | Путь | Успешный ответ |
|---|---|---|---|
| 1. Получение списка изданий | GET | `/editions?limit=20&offset=0` | 200, объект с массивом `items`. Пустой список тоже даёт 200. |
| 2. Получение одного издания | GET | `/editions/{edition_id}` | 200, сведения об издании. |
| 3. Выдача экземпляра читателю | POST | `/loans` | 201, новая выдача; `Location` указывает на неё. |
| 4. Возврат экземпляра по выдаче | PUT | `/loans/{loan_id}/return` | 201 при первом создании записи возврата, 200 с прежней записью при точном повторе. |
| 5. Продление срока выдачи | POST | `/loans/{loan_id}/renewals` | 201, отдельная запись принятого продления и новый срок. |
| 6. Постановка читателя в очередь | POST | `/reservations` | 201, бронь на издание и текущая позиция. |
| 7. Отмена брони | DELETE | `/reservations/{reservation_id}` | 204 без тела. Повторная отмена ранее существовавшей брони тоже даёт 204. |
| 8. Начисление задолженности | POST | `/debts` | 201, отдельное начисление; `Location` указывает на него. |

В операции возврата PUT передаёт полное представление отдельного ресурса возврата, а не произвольно меняет часть выдачи. Например, тело содержит `returned_at` и `condition`. Для одной выдачи такой ресурс существует не более одного раза. При повторе передаются прежние значения; другая дата или состояние уже зарегистрированного возврата дают 409. Исправление ошибочного возврата является отдельной административной задачей и в эти восемь операций не входит.

Коды 200, 201 и 204 различают ответ с представлением, создание ресурса и успех без тела. Семантика методов и этих кодов сверена с [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html), разделы 9.2, 9.3 и 15.3. Пути и библиотечные правила являются моими проектными решениями.

### Неудачные исходы

| Операции | Ошибка и реакция |
|---|---|
| Все восемь | 400 при повреждённом формате сообщения, 401 при отсутствии действительных данных входа, 403 при недостаточных правах. Сначала исправляется причина. |
| 1 | 400 при отрицательных `limit` или `offset`; клиент исправляет параметры. |
| 2 | 404, если издание отсутствует. Повтор того же адреса не создаст запись. |
| 3 | 404 при неизвестном читателе или экземпляре; 409, если экземпляр уже выдан либо читатель заблокирован. |
| 4 | 404 при неизвестной выдаче; 409 при конфликтующем возврате. |
| 5 | 404 при неизвестной выдаче; 409, если книга возвращена, есть очередь или исчерпан лимит продлений. |
| 6 | 404 при неизвестном издании или читателе; 409 при уже существующей активной брони этой пары. |
| 7 | 404 для идентификатора, который никогда не существовал; 409, если бронь уже исполнена выдачей. |
| 8 | 404 при неизвестной выдаче; 409 при повторном начислении за тот же период и основание. |

Ошибка содержит короткий код, например `copy_unavailable`, пояснение и идентификатор обращения. Персональные данные других читателей и внутренние сведения об устройстве хранилища в ответ не включаются. Сетевой тайм-аут не доказывает, что операция не выполнена: ответ мог потеряться после сохранения результата.

## 1.4. Почему продление является отдельным действием

Первый способ: частично изменить выдачу через PATCH `/loans/{loan_id}`, передав новую абсолютную дату `due_date`. Он компактен, но сам по себе не показывает, кто запросил продление, по какому правилу оно разрешено и сколько продлений уже было. Клиенту также не следует разрешать назначать произвольный срок. PATCH предназначен для частичного изменения, но не гарантирует идемпотентность сам по себе: это следует из [RFC 5789, раздел 2](https://www.rfc-editor.org/rfc/rfc5789.html#section-2).

Второй способ: создать запись в `/loans/{loan_id}/renewals`. Клиент просит продление, сервер проверяет состояние выдачи и очередь, сам вычисляет новый срок и сохраняет основание изменения.

Выбираю второй способ. Он отражает правило библиотеки и оставляет историю. Проектное правило: не более двух продлений одной выдачи, каждое на 14 календарных дней от текущего срока; продление возвращённой книги и книги с активной очередью отклоняется. Это принятые для работы допущения, а не сведения о действующих правилах университета.

## 1.5. Повторяемость и защита от дублей

| Операции | Результат одинакового повтора |
|---|---|
| 1 и 2, GET | Прикладное состояние не меняется. Ответ может отличаться, если каталог успел измениться. |
| 4, PUT возврата | Сохраняется один возврат, экземпляр освобождается один раз. Клиент повторяет ту же дату, а не подставляет новое текущее время. |
| 7, DELETE брони | Бронь остаётся отменённой. Второй запрос не отменяет следующую бронь. |
| 3, 5, 6 и 8, POST | Без дополнительной защиты повтор может создать ещё одну выдачу, ещё одно продление, бронь или начисление. Автоматический повтор по одному лишь методу не разрешён. |

Для четырёх POST-операций контракт требует заголовок `Idempotency-Key`. Это согласованное поле данного проекта. Для одной попытки клиент создаёт ключ и сохраняет его до получения окончательного результата. При сетевом повторе ключ и тело остаются прежними.

Сервер хранит область ключа, сам ключ, отпечаток тела, состояние обработки, созданный идентификатор, код и тело результата. Область включает клиента и операцию. Регистрация ключа и изменение библиотечных данных выполняются атомарно. Тот же ключ с тем же телом возвращает сохранённый результат без нового эффекта; другой текст под тем же ключом даёт 409. Пока первая операция выполняется, повтор получает 409 с кодом `operation_in_progress` и указанием проверить результат позже.

Срок хранения результата в проекте составляет 24 часа. После этого автоматический повтор прекращается до сверки по идентификатору операции. Дополнительно действуют предметные ограничения: одна активная выдача экземпляра, одна активная бронь читателя на издание, уникальное начисление за сочетание выдачи, периода и основания. Две разные просьбы с разными ключами всё равно проверяются по этим правилам.

## 1.6. Два примера обмена

Примеры показывают договор о сообщениях. Они не являются результатами сетевых обращений.

### Пример А. Выдача экземпляра

Запрос: POST `/loans`, `Content-Type: application/json`, `Idempotency-Key: loan-20261108-001`.

```json
{
  "copy_id": "C-0042",
  "reader_id": "R-0107"
}
```

Ответ: 201 Created, `Location: /loans/L-0310`, `Content-Type: application/json`.

```json
{
  "id": "L-0310",
  "copy_id": "C-0042",
  "reader_id": "R-0107",
  "issued_at": "2026-11-08T09:00:00+05:00",
  "due_date": "2026-11-22",
  "status": "active"
}
```

Срок устанавливает сервер. Если ответ потерян, повтор с ключом `loan-20261108-001` возвращает ту же выдачу `L-0310`, а не выдаёт ещё одну книгу.

### Пример Б. Продление выдачи

Запрос: POST `/loans/L-0310/renewals`, `Content-Type: application/json`, `Idempotency-Key: renewal-20261115-001`.

```json
{
  "reason": "Продолжение работы с учебником"
}
```

Ответ: 201 Created, `Location: /loans/L-0310/renewals/N-0021`, `Content-Type: application/json`.

```json
{
  "id": "N-0021",
  "loan_id": "L-0310",
  "previous_due_date": "2026-11-22",
  "new_due_date": "2026-12-06",
  "renewal_number": 1,
  "reason": "Продолжение работы с учебником"
}
```

Новый срок получен прибавлением 14 календарных дней к 22 ноября. Повтор с тем же ключом не переносит его на 20 декабря и не увеличивает счётчик.

## 1.7. Вывод

Интерфейс описан через сущности библиотеки и историю их изменений. Создание выдачи, продления, брони и задолженности отделено от чтения каталога, возврата и отмены. Главное условие повторной отправки: система должна узнавать прежнюю операцию, а не надеяться, что клиент никогда не потеряет ответ. Реализация сервера и нагрузочные испытания в выбранное задание не входят.
