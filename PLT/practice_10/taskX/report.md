В базе 5000 заказов, 5000 различных контрагентов и 15000 позиций, по три на заказ. Период `[2026-06-01, 2026-06-11)` выбирает 140 заказов и 420 позиций. Цена хранится целым числом копеек. Для каждого варианта выполнены три прогрева и семь замеров. Время включает получение строк, сборку объектов или результирующих кортежей и сортировку. Результат сравнивается целиком с эталоном вне таймера. Во время запроса счётчик `before_cursor_execute` регистрирует реальные SELECT. Журнал одного измерения каждой серии сохранён в `queries.txt`. Это тёплая локальная база без сетевой задержки; выигрыш сокращения обращений к удалённой СУБД отдельно не измерялся.

## 3. N + 1 и предварительная загрузка

Наивная версия сначала получает заказы, а при обходе обращается к `order.items` и `order.customer.name`. Получено 1 + 140 + 140 = 281 SELECT. Один запрос выбирает список, 140 загружают позиции и 140 загружают разных контрагентов. Это два независимых проявления N + 1, а не 421 запрос по числу позиций.

Исправленная версия добавляет `joinedload(Order.customer)` и `joinedload(Order.items)`. Получен один SELECT с соединениями. `unique()` убирает повторение объектов заказа из результата соединения, но не удаляет его позиции.

Фрагмент обязательного SQL-журнала:

```text
SELECT orders.id, orders.customer_id, orders.created_at FROM orders WHERE ...
SELECT items.id, items.order_id, items.title, ... FROM items WHERE ? = items.order_id
SELECT customers.id, customers.name FROM customers WHERE customers.id = ?
```

Полный текст, значения параметров и фактическое число запросов находятся в `queries.txt`.

## 4. Измерения и один SQL-запрос

| Этап | Вариант | SELECT | Медиана, с | Минимум..максимум, с |
| --- | --- | --- | --- | --- |
| before_index | lazy | 281 | 0.107905900 | 0.100273400..0.112953500 |
| before_index | eager | 1 | 0.058989400 | 0.053635400..0.066986000 |
| before_index | sql | 1 | 0.002757700 | 0.002587200..0.003162600 |
| after_index | lazy | 281 | 0.072045300 | 0.068611500..0.156979500 |
| after_index | eager | 1 | 0.011930100 | 0.009726200..0.030498000 |
| after_index | sql | 1 | 0.003368200 | 0.002790300..0.008586500 |

Ручной SQL соединяет три таблицы, фильтрует период и использует оконную сумму по заказу. Позиции возвращаются вместе с суммой заказа, сортировка задаётся `ORDER BY total DESC, o.id, i.id`. Python собирает строки обратно в тот же результат. Все три версии вернули одинаковые 140 заказов с одинаковыми именами, позициями, суммами и порядком.

## 5. План и индексы

До индексов ключевой фрагмент плана полного SQL:

```text
CO-ROUTINE (subquery-2)
CO-ROUTINE (subquery-3)
SCAN i
SEARCH o USING INTEGER PRIMARY KEY (rowid=?)
SEARCH c USING INTEGER PRIMARY KEY (rowid=?)
USE TEMP B-TREE FOR ORDER BY
SCAN (subquery-3)
SCAN (subquery-2)
USE TEMP B-TREE FOR ORDER BY
```

После `CREATE INDEX ix_orders_date ON orders(created_at)` и `CREATE INDEX ix_items_order ON items(order_id)`:

```text
CO-ROUTINE (subquery-2)
CO-ROUTINE (subquery-3)
SEARCH o USING INDEX ix_orders_date (created_at>? AND created_at<?)
SEARCH c USING INTEGER PRIMARY KEY (rowid=?)
SEARCH i USING INDEX ix_items_order (order_id=?)
USE TEMP B-TREE FOR ORDER BY
SCAN (subquery-3)
SCAN (subquery-2)
USE TEMP B-TREE FOR ORDER BY
```

Раньше движок начинал с полного обхода 15000 позиций, теперь сначала выбирает заказы по дате и ищет их позиции по внешнему ключу. Первичный ключ контрагента уже индексируется. Временная B-структура для сортировки остаётся: индекс по дате не упорядочивает результаты по вычисленной сумме. Eager ORM ускорился примерно в 4,94 раза. У ручного SQL ускорение этой серией не подтверждено: медиана после индексов 0,0033682 с выше прежних 0,0027577 с, а интервалы пересекаются. Серии не изолированы от фоновой нагрузки; отдельный вклад планировщика не измерялся. Смена полного обхода на индексный поиск доказана планом, но не гарантирует меньшего времени на маленькой локальной выборке. Индексы не исправляют число запросов lazy: после их добавления по-прежнему 281 SELECT.

## 6. Сравнение решений и отказов

| Признак | ORM с joinedload | Ручной SQL |
| --- | --- | --- |
| Запросов | 1 | 1 |
| Медиана после индексов, с | 0,011930100 | 0,003368200 |
| Объём основного кода | orm_report: 16 непустых строк | sql_report + QUERY: 23 непустых строк |
| Изменение модели | Связи и поля проверяются через отображения; миграции всё равно нужны | Имена таблиц и столбцов связаны с текстом; запрос и сборку результата приходится обновлять вручную |

Подсчёт строк исключает docstrings, но включает управляющие строки; это ориентир сопровождения, а не мера качества. На данном аналитическом чтении ручной SQL оказался быстрее. Для обычных изменений сущностей и связей ORM удобнее; для агрегатов, сложных отчётов и контроля плана SQL делает стоимость явной. Выбор не отменяет измерение запросов.

Общее требование о контролируемых отказах проверено отдельно на локальном HTTP-стенде, который отдаёт готовый отчёт. Он не включён в замеры базы:

| Режим | Управляемое поведение | Наблюдение клиента |
| --- | --- | --- |
| slow | Задержка 60 мс при сроке 20 мс | TimeoutError |
| error | HTTP 503 | HTTPError |
| disconnect | Закрытие соединения без ответа | RemoteDisconnected |
| duplicate | Каждая запись отчёта возвращается дважды | ValueError по повторному id |

Нормальный ответ прошёл проверку. Клиент проверяет типы полей, уникальность id, положительное количество, неотрицательную цену и соответствие суммы позициям. Срок 20 мс выбран только для детерминированного стенда, не как промышленная рекомендация. Автоматические повторы не добавлялись: задача посвящена ORM. Обрыв и ошибка завершились обнаруженным исключением, а не успешным неполным отчётом.

## 7. Проверки и воспроизведение

Пустой период без заказов возвращает пустой список. Предельный корректный диапазон от 0001-01-01 до 9999-12-31 возвращает все 5000 заказов в обеих реализациях. Некорректная дата и обратный период отвергнуты обеими реализациями. Основные данные включают первый и последний день полуоткрытого диапазона; повторяемость сумм разрешается сортировкой по id. Средства ORM не подменяются словарём или самодельным отображением.

Из корня репозитория:

```text
python -m venv "$env:TEMP/plt10-env"
& "$env:TEMP/plt10-env/Scripts/python.exe" -m pip install -r PLT/practice_10/taskX/requirements.txt
& "$env:TEMP/plt10-env/Scripts/python.exe" -X utf8 PLT/practice_10/taskX/task4.py
```

Фактический запуск завершился с кодом 0, строками `FAULTS={...}` для четырёх отказов и `ORM_SQL_EQUAL ORDERS=140 TRIALS=7 WARMUP=3 EDGE_CASES=8 OK`. Результаты и SQL-журнал при повторном запуске перезаписываются.

### 7.1. Отдельные проверки границы и повторной доставки

Дополнительная команда без повторного измерения производительности:

```text
& "$env:TEMP/plt10-env/Scripts/python.exe" -B -X utf8 PLT/practice_10/taskX/test_task4.py
```

Фактический вывод, код завершения 0:

```text
CANONICAL_DATES: VALID=1 REJECTED=8 OK
APP_DELIVERY: DELIVERIES=2 APPLIED=1 DUPLICATES=1 ROWS=140 OK
REQUEST_ID_COLLISION: REJECTED=1 OK
```

Исправлена граница дат: `date.fromisoformat` принимает также `20260601` и `2026-W23-1`, однако такие исходные строки непригодны для сравнения с сохранёнными YYYY-MM-DD. После парсинга функция сравнивает каждую исходную строку с `isoformat()` и отвергает неканонический ввод. Проверены обе формы в начале и конце периода у обеих реализаций, до обращения к соединению.

Повторная доставка проверена отдельно от HTTP. Один прикладной ответ из 140 реальных заказов сериализован с `request_id`, затем дважды помещён в локальную очередь. Получатель обработал две доставки, но применил состояние один раз: повтор с тем же идентификатором и содержимым пропущен. Повторное использование идентификатора с другими данными вызывает ValueError. Это модель повторной прикладной доставки, не попытка отправить два HTTP-ответа на один HTTP/1.1-запрос.

Режим HTTP `duplicate` из предыдущей таблицы остаётся дополнительной проверкой повторяющихся записей внутри одного ответа 200. Он сам по себе не доказывает обработку повторной доставки. Дедупликация здесь хранится в памяти одного процесса; устойчивость после перезапуска и распределённые получатели не проверялись.

## 8. Вывод

Скрытая загрузка связанных объектов увеличила число SELECT до 281. Предварительная загрузка уменьшила его до одного, а индексы изменили план поиска внутри этого запроса. Ручной SQL оказался самым быстрым на этой выборке, но требует явного сопровождения схемы и сборки результата. Число запросов и план выполнения объясняют результат лучше, чем внешний вид ORM-кода.
