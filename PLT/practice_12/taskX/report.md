## 1. Выбор задания и контракт функции

Выбрано задание 4. Оно допускает один Python и небольшой модуль, не требует развёртывания сети, второго языка или рефакторинга чужого проекта объёмом 200 строк. Использованы настоящие инструменты coverage.py 7.17.2 и Cosmic Ray 8.8.0. Среда: Windows 11, Python 3.13.15.

Функция `discount(amount, member)` возвращает размер скидки в целых денежных единицах. Отрицательная сумма недопустима. Для суммы меньше 100 скидка равна нулю. Начиная со 100 включительно обычный покупатель получает 10 процентов, участник программы 20 процентов. Дробная часть отбрасывается, верхний предел скидки равен 500. Предполагаются целочисленный `amount` и логический `member`; проверка типов внешнего ввода не входит в этот небольшой модуль.

Исходный `discount_buggy.py` использует условие `amount <= 100`, поэтому для суммы 100 возвращает 0 вместо 10. В окончательном `discount.py` условие заменено на `amount < 100`.

## 2. Полное покрытие при существующем дефекте

Набор `test_weak.py` один раз проверяет исключение для отрицательной суммы, затем вызывает функцию для нуля, порога 100 и положительных сумм с обеими ставками. Для обычных результатов утверждений нет. Это намеренно плохой набор, а не рекомендуемый стиль тестирования.

Реальный вывод coverage.py для ошибочной версии:

```text
Name          Stmts   Miss Branch BrPart  Cover   Missing
---------------------------------------------------------
discount.py       7      0      4      0   100%
---------------------------------------------------------
TOTAL             7      0      4      0   100%
```

Все семь учитываемых операторов и четыре учитываемых перехода исполнены. Дефект при `amount = 100` при этом не замечен: результат вызова не сравнивается с требованием. Усиленный набор на том же исходнике реально завершился кодом 1 с `AssertionError: 0 != 10`.

Покрытие строк отвечает, исполнялись ли операторы. Покрытие ветвей дополнительно учитывает исходы переходов, но не все значения внутри ветви. Покрытие условий проверяет истинность и ложность отдельных логических условий; для простого сравнения в данном примере оба исхода также уже присутствуют. Поэтому даже переход к покрытию ветвей и условий сам по себе здесь дефект не обнаружит. Нужны проверка результата и граничные данные 99, 100, 101. Измерение переходов coverage.py описано в [официальной документации](https://coverage.readthedocs.io/en/latest/branch.html).

## 3. Мутационный анализ

`experiment.py` создаёт временную копию, запускает `cosmic-ray baseline`, `init`, `exec` и `cr-report --show-diff`. Исходные файлы сдаваемой работы не мутируют. Для каждого варианта создаётся отдельная база сеанса. Команды, коды, длительности и все различия мутантов сохранены в `results.json`.

| Вариант | Мутантов | Выжили | Доля выживших | Время exec, с |
|---|---:|---:|---:|---:|
| Ошибочная функция, слабые тесты | 49 | 41 | 83,67% | 4,545377 |
| Исправленная функция, те же слабые тесты | 49 | 41 | 83,67% | 4,470011 |
| Исправленная функция, усиленные тесты | 49 | 0 | 0% | 4,558063 |

Средний вариант нужен, чтобы не приписать эффект тестам, одновременно изменив функцию. На одной и той же исправленной функции число выживших снизилось с 41 до 0 после замены набора тестов. Во всех трёх вариантах baseline и команды инструмента завершились кодом 0. Запуск всех фаз занимает больше `exec`: в него входят инициализация, исходный прогон, отчёт и запуск дочерних процессов.

## 4. Пять выживших мутантов

Все пять взяты из реального отчёта первого прогона, а не придуманы после измерения. Операторы изменяют умножение в выражении `min(amount * rate // 100, 500)`.

| Мутация | Результат при amount=105, member=True | Классификация | Какая проверка её обнаруживает |
|---|---:|---|---|
| `amount + rate // 100` | 105 вместо 21 | Пробел тестов | Сравнение с 21 |
| `amount - rate // 100` | 105 вместо 21 | Пробел тестов | Сравнение с 21 |
| `amount / rate // 100` | 0.0 вместо 21 | Пробел тестов | Сравнение с 21 |
| `amount // rate // 100` | 0 вместо 21 | Пробел тестов | Сравнение с 21 |
| `amount % rate // 100` | 0 вместо 21 | Пробел тестов | Сравнение с 21 |

Это достижимые изменения результата, а не недостижимый код или эквивалентные мутации. Их пропустил набор, который вызывал расчёт, но не проверял возвращённое число. В усиленном наборе этот пробел закрыт `test_member_rate_and_integer_rounding`.

Остальные усиленные тесты проверяют исключение, включённую границу, ноль и предел 500. Они также проверяют значения 2499, 2500 и 5000 для участника: скидка соответственно 499, 500, 500. Обнаружение всех мутантов означает пригодность набора против данного конечного набора операторов, но не доказательство правильности для всех ошибок.

## 5. Воспроизведение

Из каталога задания на Windows:

```powershell
python3.13 -m venv "$env:TEMP\plt12-env"
& "$env:TEMP\plt12-env\Scripts\python.exe" -m pip install -r requirements.txt
& "$env:TEMP\plt12-env\Scripts\python.exe" -B -X utf8 experiment.py
python3.13 -B -X utf8 -m unittest -v test_discount.py
```

Версии двух основных инструментов закреплены в `requirements.txt`. Установка в окружение и соединение с индексом пакетов нужны для первого воспроизведения, но не входят в измеренное время мутационного анализа. Транзитивные зависимости не закреплены отдельным lock-файлом, поэтому это фиксация версий анализаторов, а не побайтово идентичная поставка всего окружения.

Конечный вывод: `EXPERIMENT_OK`, код 0. Усиленный набор выполнил четыре теста: `Ran 4 tests in 0.000s`, `OK`. Внешний замер процесса с этим набором составил 0,073155 с; значение 0,000 внутри unittest означает округление, а не нулевую стоимость. При повторе длительности изменятся.

## 6. Стоимость и вывод

На модуле из семи операторов один прогон 49 мутантов занял около 4,5 с. Это допустимо для учебной работы. Грубая оценка при неизменной стоимости тестового процесса линейна по числу мутантов. Для большого проекта она перестаёт быть точной: меняются длительность набора, доля невалидных мутаций, кэширование и возможность отбора тестов. Быстрые тесты разумно запускать постоянно, а полный мутационный анализ отдельно для изменённых модулей.

Заказчику я бы предъявил не одно число покрытия, а проверенные требования и границы вместе с долей обнаруженных значащих мутантов, описанием выживших и историей регрессионных тестов. В опыте 100% покрытия не обнаружили реальную ошибку на пороге. Только утверждения по контракту и проверка границ превратили исполнение кода в содержательную проверку.
