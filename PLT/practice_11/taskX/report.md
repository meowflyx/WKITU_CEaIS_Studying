## 1. Выбор задания и условия опыта

Выбрано задание 1: классифицировать десять отказов службы заявок и реализовать три стратегии на двух языках. Оно позволяет выполнить опыт без внешних служб и дополнительных пакетов. Задания 2 и 4 требуют других языков, задание 3 требует большого разборщика и случайных испытаний, а задание 5 отдельно требует двух независимых разборов журнала людьми.

Служба условно проходит этапы приёма файла, проверки количества, обращения к справочнику, сохранения двух записей и отправки уведомления. Ошибки файла, справочника и уведомления внедряются через аргумент `scenario`, а не через реальную сеть. Python использует настоящую SQLite в оперативной памяти; Julia использует вектор как упрощённое хранилище. Это проверка стратегий, а не испытание сетевого клиента и не сравнение производительности языков.

Среда: Windows 11, Python 3.13.15, Julia 1.12.7. Обе программы используют только встроенные средства своих языков. Предварительная таблица сохранена в `plan.md` до реализации и первого запуска.

## 2. Классификация и фактические исходы

`STOP` означает прекращение текущей операции, `OK` означает полный успех, `PARTIAL` означает сохранённый основной результат при недоступном уведомлении. Число попыток относится только к справочнику; ноль означает, что до него выполнение не дошло. Все десять отказов воспроизведены в обеих реализациях.

| Сценарий | Отказ и класс | Стратегия | Фактический исход Python и Julia | Что получает пользователь |
|---|---|---|---|---|
| empty | Пустой файл, ошибка данных | Прекратить | STOP, 0 попыток, 0 записей | Название поля file и причина |
| quantity | Количество -1, ошибка данных | Прекратить | STOP, 0 попыток, 0 записей | Поле quantity, требуется значение не меньше 1 |
| missing_file | Нет входного файла, отказ окружения | Прекратить | STOP, 0 попыток, 0 записей | Файл input.csv отсутствует |
| timeout_once | Один таймаут, временный отказ окружения | Повторить до 3 раз | OK, 2 попытки, 2 записи | Полный результат после повторной попытки |
| timeout_always | Таймаут на каждой попытке, отказ окружения | Ограниченный повтор | STOP, 3 попытки, 0 записей | Справочник не ответил в срок |
| catalog_contract | Нет обязательного кода, нарушение внешнего контракта | Прекратить | STOP, 1 попытка, 0 записей | Название отсутствующего поля catalog.code |
| capacity | 101 строка при лимите 100, исчерпание ресурса | Ограничить объём и прекратить | STOP, 0 попыток, 0 записей | Лимит и полученное число строк |
| invariant | Отрицательный внутренний итог, дефект программы | Ранний отказ | STOP, 1 попытка, 0 записей | Отказ операции, а не фиктивная нулевая сумма |
| partial_save | Сбой между двумя сохранениями, отказ окружения | Откатить всю транзакцию | STOP, 1 попытка, 0 записей | Операция не сохранена |
| notify | Уведомление недоступно, отказ окружения | Продолжить с частичным результатом | PARTIAL, 1 попытка, 2 записи | Данные сохранены, уведомление не доставлено |

Для неправильных данных повтор ничего не исправляет. Для временного таймаута повтор имеет смысл, но ограничен тремя попытками. Для уведомления допустимо ухудшение обслуживания: данные уже сохранены, поэтому изображать полный отказ и предлагать повтор всей заявки опасно. Признак неполноты возвращается явно.

## 3. Расхождение плана с поведением

Первоначально для отказа после первой записи был выбран повтор всей операции. Опыт `partial_save_demo()` показал, что это решение неверно без дополнительных условий.

| Этап реального опыта SQLite | Число записей |
|---|---:|
| Первая запись отдельно зафиксирована, затем вызван сбой | 1 |
| После этого слепо повторены обе записи | 3 |
| Оба INSERT объединены одной транзакцией, сбой вызван после первого | 0 |

Буквальный результат программы: `PARTIAL_SAVE (1, 3, 0)`. Первое число показывает частичное состояние, второе показывает дубликат после повтора, третье показывает откат исправленного варианта. План не учитывал, что факт получения исключения не означает отсутствие побочных эффектов.

В исправленном Python-коде обе вставки находятся внутри `with database`. При исключении незавершённая транзакция откатывается; закрытие соединения отдельно выполняет `closing`. Поведение менеджера транзакций описано в [документации sqlite3](https://docs.python.org/3.13/library/sqlite3.html#how-to-use-the-connection-context-manager). В Julia перед изменением вектора запоминается длина, а обработчик возвращает эту длину и повторно передаёт исключение выше. Это учебный откат локального состояния, а не гарантия долговечности базы данных.

Для настоящей службы дополнительно нужен ключ идемпотентности заявки: если ответ потерян после успешного COMMIT, клиент может повторить уже выполненную операцию. Одна транзакция не решает эту отдельную проблему. Доставку уведомления можно вынести в очередь исходящих сообщений с повтором по идентификатору, не повторяя сохранение заказа.

## 4. Ошибка данных и дефект программы

Ошибка данных нарушает проверяемый контракт на границе: количество -1 поступило извне, а функция обязана его отклонить. Дефект программы нарушает предположение после проверки: при положительном количестве и фиксированной положительной цене внутренний итог оказался отрицательным. Здесь подстановка нуля скрыла бы ошибку расчёта.

В Python внутренний дефект представлен `ArithmeticError`, в Julia `DomainError`. Для учебного сценария он преобразуется в `STOP`, после чего вычисление не продолжается. Неизвестные ошибки не перехватываются как ожидаемые. В Julia общий `catch` нужен для отката вектора, но после отката выполняется `rethrow()`. Само наличие обработчика ещё не означает подавление исключения.

Обработчики Python перечисляют ожидаемые типы. Сообщение сохраняет имя типа и текст причины. Это компактный вывод стенда, а не промышленная трассировка: полного стека и сквозного журнала в задании 1 нет. В реальной службе внутреннюю диагностику следует отделить от ответа пользователю.

## 5. Проверка и воспроизведение

Команды выполняются из каталога задания:

```powershell
python3.13 -B -X utf8 task1.py
python3.13 -B -X utf8 -m unittest -v test_task1.py
julia --startup-file=no task1.jl
```

Выполнены четыре Python-теста: десять отказов и состояния, предел повторов, частичное сохранение с откатом, обычный успех и неполное уведомление. Итог `Ran 4 tests ... OK`, код завершения 0. Julia проверяет те же десять исходов, предел попыток и обычный успех через `@assert`. Итог `JULIA_OK: 10 failures, retry limit, normal case`, код 0. Полный вывод сохранён в `execution.txt`.

Сценарий `normal` дополнительно возвращает `OK` с двумя записями. Пустой, отрицательный и превышающий лимит входы представлены отдельными случаями. Граница количества 1 не вынесена в отдельный внешний интерфейс: стенд принимает название сценария, а не произвольный файл.

Общий пункт практикума о независимой оценке диагностики однокурсником остаётся отдельной человеческой проверкой. Автоматические тесты подтверждают состояния, но не измеряют понятность сообщений постороннему человеку. Такого замера в данной работе не заявляется.

## 6. Вывод

Одинаковое слово «ошибка» не задаёт одинаковую реакцию. Некорректные данные прекращают операцию до записи, временный таймаут допускает ограниченный повтор, а отказ необязательного уведомления допускает явно неполный результат. Самое важное расхождение опыта с планом связано с частичной записью: простой повтор оставил три строки вместо двух. Транзакционный откат сохранил ноль строк при неудачной операции.
