## Задание 1.

В этом задании нужно обработать список записей. Каждая запись состоит из
идентификатора товара, его цены и количества. Для каждого идентификатора
нужно вычислить суммарную стоимость по формуле:

`суммарная стоимость = цена * количество`

Если один идентификатор встречается несколько раз, стоимости этих записей
нужно сложить. После этого результат требуется вывести по убыванию
суммарной стоимости.

В этом отчете я сравниваю только Python и Julia. Реализации на C и Java не
добавлялись, потому что в рамках этой работы я решил не делать вид, что знаю
языки, которые пока не изучал достаточно для уверенной проверки результата.

### Общий тест

Для проверки я использовал такие данные:

```text
("samsung", 100, 2)
("poco", 50, 5)
("iphone", 120, 1)
("samsung", 80, 1)
```

Идентификатор `samsung` специально записан дважды. Это проверяет не только
умножение цены на количество, но и правильное объединение нескольких записей.
Ожидаемые суммы такие:

- `samsung`: `100 * 2 + 80 * 1 = 280`;
- `poco`: `50 * 5 = 250`;
- `iphone`: `120 * 1 = 120`.

Ожидаемый порядок результата: `samsung`, `poco`, `iphone`.

### Реализация на Python

В Python для накопления сумм используется словарь `dict`. Идентификатор
становится ключом словаря, а сумма - его значением. Метод `get` позволяет
получить уже накопленное значение. Если ключ встречается впервые, вместо него
используется ноль.

В конце вызывается `sorted`. Параметр `key=lambda item: item[1]` означает,
что сортировать нужно по сумме, то есть по второму элементу каждой пары.
Параметр `reverse=True` меняет порядок на убывающий.

Результат запуска:

```text
[("samsung", 280), ("poco", 250), ("iphone", 120)]
```

### Реализация на Julia

В Julia используется `Dict{String, Int64}`, то есть словарь со строковыми
ключами и целыми значениями. Цикл `for` сразу распаковывает каждую запись на
три переменные: идентификатор, цену и количество.

После накопления сумм словарь преобразуется в массив пар функцией `collect`.
Это необходимо, потому что сортировать нужно уже полученный массив. Функция
`sort` сортирует пары по второму элементу, а `rev=true` задает убывание.
Последним выражением результат переводится из Julia-типа `Pair` в обычные
кортежи `(идентификатор, сумма)`, чтобы результат был похож на Python-версию.

Результат запуска:

```text
[("samsung", 280), ("poco", 250), ("iphone", 120)]
```

### Проверка типов

`mypy` нужен для отдельного сравнения: обычный Python проверяет код во время
выполнения, а `mypy --strict` анализирует аннотации до запуска. Поэтому он
может обнаружить несовпадение типов даже без специальной входной записи.

Команда была реально выполнена в Python 3.12.10:

```text
python -m mypy --strict .\practrice_1\task1.py
```

Фактический результат:

```text
task1.py:15: error: Need type annotation for "totals" [var-annotated]
task1.py:31: error: Argument 1 to "total_by_id" has incompatible type
"list[tuple[str, int, int]]"; expected "list[tuple[str, float, int]]" [arg-type]
Found 2 errors in 1 file (checked 1 source file)
```

Это обнаружение происходит на стадии **проверки типов**, до запуска программы.
Первая ошибка означает, что строгий режим требует явно написать тип словаря.
Вторая показывает реальное несоответствие: функция обещает `float`, а тестовые
данные содержат `int`. Обычный Python при этом запускается успешно, потому что
целые числа подходят для используемого умножения.

Для Julia была выполнена команда с `@code_warntype`:

```text
julia -e 'using InteractiveUtils; include(raw".\practrice_1\task1.jl"); @code_warntype total_by_id(records)'
```

В отчете `@code_warntype` показал конкретные типы:
`Vector{Tuple{String, Int64, Int64}}` на входе,
`Dict{String, Int64}` внутри и `Vector{Tuple{String, Int64}}` на выходе.
Неопределенного `Any` в вычислениях нет, поэтому функция типостабильна.
Это дополнительная проверка во время разработки, а не отдельный запуск
дефектных данных.

### Итог

Python обычно быстрее писать, но без `mypy` часть проблем с типами видна только
во время выполнения. Julia раньше отсекает несовместимую сигнатуру метода, но
фиксированный `Int64` не защищает от переполнения. Поэтому ранняя проверка
типов особенно важна для платежей, финансовых расчетов, складских остатков и
научных вычислений: там неверный результат хуже остановки программы.

Для небольших скриптов и учебных задач скорость написания Python может быть
важнее. Для ответственных проектов различие стадий обнаружения перевешивает
разницу в скорости написания, но только вместе с тестами границ числовых типов.

Хочу также добавить, что для написании части кода Julia и для комментариев я использовал Codex,
что-бы самому глубже понимать что происходит. Иногда это проще чем читать документацию, и быстрее.
Главное понимать что кодекс по итогу пишет, и для меня важно то, что я это всё понял.
