## Что проверяется

Заявка на пропуск бывает в одном из четырёх состояний.

| Состояние | Что обязательно | Чего быть не должно |
|---|---|---|
| черновик | ничего | дата подачи, утвердивший, срок, причина |
| подана | дата подачи | утвердивший, срок, причина |
| одобрена | утвердивший, срок действия | причина отказа |
| отклонена | причина отказа | утвердивший, срок действия |

В первой, наивной модели есть один класс `PassRequest`. В нём все поля необязательные, а состояние хранится строкой. Поэтому неверную заявку сначала можно создать, и только `validate` найдёт ошибку.

Во второй модели каждое состояние - отдельный класс или структура. Например, `Rejected` вообще не содержит поля `valid_until`. Значит, срок действия нельзя нормально добавить к отклонённой заявке.

## Python

В Python новая модель состоит из классов `Draft`, `Submitted`, `Approved` и `Rejected`. Тип `Request` объединяет их. Для проверки кода используется mypy.

| № | Попытка создать неверную заявку | Можно ли написать при проверке mypy? | Ошибка mypy |
|---|---|---|---|
| 1 | `Draft(submitted_at=date(2026, 9, 22))` | нет | `Unexpected keyword argument "submitted_at" for "Draft"` |
| 2 | `Submitted(None)` | нет | `Argument 1 to "Submitted" has incompatible type "None"; expected "date"` |
| 3 | `Approved(None, date(2026, 12, 31))` | нет | `Argument 1 to "Approved" has incompatible type "None"; expected "int"` |
| 4 | `Approved(123, None)` | нет | `Argument 2 to "Approved" has incompatible type "None"; expected "date"` |
| 5 | `Rejected("Неверные данные", valid_until=date(2026, 12, 31))` | нет | `Unexpected keyword argument "valid_until" for "Rejected"` |

mypy нашёл ровно 5 ошибок. Сам файл `task1.py` проходит `mypy --strict` без ошибок.

Но Python сам по себе не проверяет типы аннотаций во время запуска. Если не запустить mypy, выражения 2, 3 и 4 создают объект с `None` вместо обязательного значения. Выражения 1 и 5 всё равно падают: у соответствующих конструкторов нет такого поля.

Итог по Python: с mypy все 5 случаев становятся ошибками до запуска программы. Без mypy защита неполная: 3 случая всё ещё можно создать.

## Julia

В Julia есть абстрактный тип `Request` и четыре подтипа: `Draft`, `Submitted`, `Approved`, `Rejected`.

```julia
abstract type Request end

struct Submitted <: Request
    submitted_at::Date
end
```

`<:` означает «является подтипом». `Submitted` обязан получить `Date`, поэтому `nothing` туда не подходит. `Draft` не имеет полей вообще. В `Rejected` нет поля со сроком действия.

Для `Approved` написан короткий конструктор:

```julia
Approved(approved_by::Int, valid_until::Date) =
    Approved(approved_by, valid_until, nothing)
```

Он позволяет создать одобренную заявку с двумя обязательными значениями. Третье поле - дата подачи - необязательное и поэтому получает `nothing`.

### Попытки нарушения в Julia

| № | Попытка | Можно ли создать объект? | Текст ошибки |
|---|---|---|---|
| 1 | `Draft(Date(2026, 9, 22))` | нет | `MethodError: no method matching Draft(::Date)` |
| 2 | `Submitted(nothing)` | нет | `MethodError: Cannot convert an object of type Nothing to an object of type Date` |
| 3 | `Approved(nothing, Date(2026, 12, 31))` | нет | `MethodError: no method matching Approved(::Nothing, ::Date)` |
| 4 | `Approved(123, nothing)` | нет | `MethodError: no method matching Approved(::Int64, ::Nothing)` |
| 5 | `Rejected("Неверные данные", nothing, Date(2026, 12, 31))` | нет | `MethodError: no method matching Rejected(::String, ::Nothing, ::Date)` |

Все пять неправильных объектов Julia не создаёт. Но это не ошибка компиляции в обычном смысле: функцию с такой строкой можно написать, а `MethodError` появится только при её вызове.

Функции `describe` и `can_enter` используют несколько методов:

```julia
can_enter(::Draft) = false
can_enter(::Submitted) = false
can_enter(::Approved) = true
can_enter(::Rejected) = false
```

Julia сама выбирает нужную строку по типу переданного объекта. Это называется множественной диспетчеризацией. Здесь всё проще: тип заявки определяет, разрешён ли проход.

## Новое состояние «аннулирована»

Проверка делалась во временных файлах, поэтому в итоговом коде осталось четыре исходных состояния.

В Python был добавлен класс `Cancelled` и включён в `Request`. Обработчики `describe` и `can_enter` специально не менялись. В конце каждого из них есть `assert_never(request)`. mypy сразу указал на оба забытых места:

```text
error: Argument 1 to "assert_never" has incompatible type "Cancelled"; expected "Never"
```

В Julia был добавлен:

```julia
struct Cancelled <: Request end
```

Julia спокойно принимает этот новый тип и не требует менять старые функции. Ошибка появится только если вызвать `describe(Cancelled())` или `can_enter(Cancelled())`:

```text
MethodError: no method matching describe(::Cancelled)
MethodError: no method matching can_enter(::Cancelled)
```

| Вопрос | Python с mypy | Julia |
|---|---|---|
| Находит все забытые обработчики до запуска | да, если есть `assert_never` | нет |
| Что происходит при добавлении нового состояния | mypy показывает ошибки | Julia молчит |
| Что происходит при вызове необработанного варианта | не должен дойти до запуска после mypy | `MethodError` |

## Сколько тестов больше не нужно

| Вариант | Сколько из 5 проверок сочетаний можно убрать |
|---|---:|
| Python с mypy | 5 из 5 |
| Python без mypy | только 2 из 5 |
| Julia | 5 из 5 |

В Julia объекты всё равно не создаются, но отказ происходит во время запуска. Поэтому это полезная защита, но не статическая проверка, как у mypy.

## Вывод

Наивная модель допускает все пять неверных заявок, пока не будет вызван `validate`.

Python с mypy не даёт написать все пять неверных вариантов и показывает места, которые забыли обновить после добавления нового состояния. Без mypy Python частично теряет эту защиту.
